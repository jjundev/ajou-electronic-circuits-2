# 전자회로2 영상 성능 가설 검증 — 2026-10-10

**Scope:** 기존 P10.72 문제풀이 영상의 동결된 화면·음성을 사용한 렌더/자막 시험. 대본 작성·TTS·교육 내용 검토의 시간은 포함하지 않는다.
**Gate:** CONDITIONAL — 이 문항의 멀티코어 렌더 개선은 검증됐으며, 다른 복습 영상에 대한 일반화와 생산 설정 변경은 별도 적용 범위다.

CPU 인코딩과 Metal 화면 캡처를 유지한 채 작업자 2개에서 6개로 늘리면 전체 렌더 평균이 **176.64초 → 85.10초**, **51.8% 단축**됐다. 2·4·6개 CPU 인코딩 결과는 파일 SHA256 및 7,220프레임의 디코딩 결과가 모두 같다. GPU 인코딩 옵션과 실험적 고속 캡처에서는 시간 단축을 확인하지 못했다.

## 시험 조건

- M5 MacBook Pro, CPU 10코어, GPU 10코어, 메모리 16GB.
- 1920×1080, 30fps, 7,220프레임, 240.6667초의 동일한 원본 composition.
- HyperFrames 0.8.137, FFmpeg 9.0.2. 패키지·소스·실제 제작 설정을 변경하지 않았다.
- 모든 주요 시험은 Metal 브라우저 + disk screenshot 캡처. 고속 캡처는 명시적으로 끄고 2/4/6개 작업자 수와 인코더 옵션만 비교했다.
- 시험은 순차 실행했다. 기본 2개와 가장 빠른 후보 6개를 2회 측정했다. 4개/GPU/자막 및 8초 브라우저 시험은 각 1회다.
- /usr/bin/time의 real 값을 사용한다. CPU 작업 시간은 user+sys의 합계이며 GPU 사용률 측정값이 아니다. RSS는 1초 간격 프로세스 트리 RSS의 합계로, 공유 페이지가 중복 집계되거나 순간 최댓값이 누락될 수 있다. 시스템 swap은 시험 프로세스만의 값이 아니다.

HyperFrames의 --gpu는 VideoToolbox를 선택했지만 내부 옵션 -allow_sw 1이 소프트웨어 대체를 허용하므로, 그 시험만으로 실제 하드웨어 실행을 인증할 수는 없다. CPU/VideoToolbox의 비트레이트 제어가 달라 화질이 같은 조건의 순수 인코더 속도 비교로 해석하지 않는다.

## 실제 하드 자막 인코딩

원본 음성을 한 번 mux한 동일한 마스터와 기존 SRT·Pretendard·libass 설정으로 비교했다. 오디오는 복사했다.

| 설정 | 전체 초 | CPU 작업 초 | RSS 합계 표본 최댓값 MiB | 출력 MiB |
|---|---:|---:|---:|---:|
| captions-current | 15.30 | 87.01 | 780 | 8.72 |
| captions-fast | 16.55 | 105.23 | 695 | 8.58 |
| captions-hardware | 26.53 | 23.23 | 206 | 37.42 |

- current: libx264 CRF18, 현재 기본 프리셋. fast: 동일 CRF18, preset fast. hardware: h264_videotoolbox, allow_sw 0, 목표 비트레이트 15M.
- hardware 시험은 소프트웨어 대체를 금지한 상태에서 성공해 하드웨어 인코딩 가능 여부를 검증했다. 현재 설정보다 느렸지만 CPU 작업량과 RSS 합계는 낮았다.
- CRF와 목표 비트레이트는 동등한 화질 설정이 아니다. 현재 설정의 결과를 기준으로 유사도를 비교했으며 무손실 원본 대비 화질 점수는 아니다.

## 브라우저 및 고속 캡처 진단

동일한 60–68초 구간을 8초의 시험용 composition으로 복사했다. 4개 작업자·동일 CPU 인코딩 조건이다.

| 방식 | 전체 초 | 실제 결과 |
|---|---:|---|
| A-metal-screenshot | 8.54 | screenshot |
| B-software-screenshot | 8.38 | screenshot |
| C-metal-fast | 11.08 | 정확도 검사 실패 후 screenshot 재시도 |

고속 캡처 자체의 검증은 60/120/180프레임에서 PSNR 23.1/22.9/22.7dB로 기준 32dB를 충족하지 못했다. 최종 일반 캡처 재시도 결과만 240프레임 모두 baseline과 같다. 고속 캡처가 올바르게 작동한 결과로 해석하면 안 된다. Metal/소프트웨어의 작은 전체 시간 차이는 한 번의 8초 시험으로 일반화할 수 없다.

## 출력 검증

- 모든 전체 길이 렌더에서 1920×1080/30fps/7,220프레임을 확인하고 전체 프레임을 디코딩했다.
- CPU 결과 5개의 모든 프레임과 파일 해시가 같다.
- 자막 영상 3개는 전체 비디오·오디오 디코딩을 통과했다. AAC 복사 데이터 해시가 같아 자막 방식 변경 중 오디오는 동일했다.
- 원래 RUN의 source/composition 및 master/final/WAV/SRT, 67개 파일의 전후 해시가 같다. 본 날짜 폴더 루트에는 별도 배포 MP4가 없어 추가 배포 파일 비교 대상은 0개였다.
- 실음성 청취·교육 내용의 새 승인·최종 게시를 수행한 시험이 아니다. 기존 동결 자료의 성능과 출력 대응만 확인했다.

## 검증된 적용 전제

- 같은 영상에서는 기존 Metal + CPU 인코더에 캡처 작업자 6개를 적용하는 방향이 가장 빠른 측정 결과를 얻었다.
- 여러 영상을 동시에 제작할 경우 각 영상마다 6개씩 늘리는 대신 전체 작업자 예산과 메모리 상태를 함께 제어할 필요가 있다. 이 동시 제작 정책은 이번 시험에서 검증하지 않았다.

## 조건과 가정 제한

- 단일 문항, 반복 횟수 1–2회, 현재 맥과 앱 부하 조건이다. 전체 대본 작성·TTS·내용 검토 시간의 52% 단축을 뜻하지 않는다.
- Hardware encoding과 일반 GPU compute/Metal 화면 합성은 서로 다른 경로다.
- GPU/CPU 인코더의 화질이 같다고 가정하지 않는다.
- 소스는 변경하지 않았고 실험적 기능을 강제 활성화한 제작 결과를 게시하지 않았다.
