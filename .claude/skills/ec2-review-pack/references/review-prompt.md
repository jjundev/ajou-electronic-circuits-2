# 리뷰어 지시문

역할·파일 인계는 [delegation.md](delegation.md)를 따른다. 기계 예비 검사 전 개인화 감사는 작성자가 아닌 전담 감사자가 수행하며, 아래 내용 리뷰어가 실제 근거를 재검토·보완한다. 실제 감사 결과는 전담 감사자가 기록한다.

상세 리뷰는 `<RUN>/work/review/report.md`에 남긴다. 부모에게는 상태·보고/감사 파일 경로·미해결 및 조치 항목의 `where`(topic ID 또는 문제 ID)·`severity`·담당 owner만 8줄 이내로 반환한다. 많은 항목은 보고 파일의 경로와 개수로 알리며 자료 전문·전체 유도·감사 본문을 메시지에 붙이지 않는다.

## 병렬 RUN의 검토 기록

브리프에 `workflow=parallel`이 있으면 두 검토자는 각각 `note`의 고정본을 읽고 자기 attempt의 `report`와 `audit_output`에 기록한다. 감사의 모든 토픽에 실제로 바인딩한 검토자 ID를 쓴다. 두 검토가 모두 통과하면 실행기가 근거를 합친다. 같은 토픽·규칙의 적용 여부가 엇갈리면 두 보고의 원문 근거를 다시 대조한다.

결함이 있으면 receipt의 `status`를 `needs-fix`로 두고 `unresolved`에 결함별로 다음 필드를 남긴다. `rule`은 규칙, `target`은 회차가 바뀌어도 찾을 수 있는 토픽·문항·그림·쪽 ID, `defect`는 해당 위치의 구체적인 오류다. 같은 오류를 다시 확인할 때는 이 세 값을 유지한다. `severity`는 Critical, Important, Minor 중 하나이며 `owner_task`는 수정할 파일을 만든 선행 작업 ID다. `evidence`에는 원문과 실제 산출물에서 확인한 근거를 적는다. 보고서의 심각도 소제목 아래 각 결함을 `- [target] [rule] defect` 한 줄로 적는다. 세 값은 해당 unresolved 항목과 정확히 일치해야 한다. 화면 결함은 실제 PNG를 outputs에 포함한다.

수정본을 받은 검토자는 브리프의 `recheck_findings`를 모두 확인한다. 요청된 각 수정의 `fix_results`에 `finding_id`, `request_id`, 작성자의 `attempt`, `outcome`(resolved 또는 unresolved), 새 `evidence`를 적는다. 미해결 항목은 `unresolved`에도 같은 키로 다시 기록한다. 다른 결함 때문에 같은 작성자가 그사이 새 수정본을 제출했다면 브리프의 `repair_outputs`와 해당 수정본에서 조립된 `repair_candidate`가 있으면 이를 열어 현재 후보와 각각 대조한다. 지정된 `repair_attempt`의 수정 결과만 해당 결함의 횟수에 반영하므로 두 버전에서 확인한 근거를 구분해 쓴다. 같은 작성자의 다른 수정에서 함께 고쳐진 기존 결함은 현재 후보를 직접 확인하고 `reconciliations`에 `finding_id`, `prior_review_attempt`, `evidence`를 기록한다.

## 문제 해설의 순서·제목·수식 행

문제 해설(자식 ec2-problem-explain)은 **문제를 읽어요 → 이 개념과 공식을 떠올려요 → 종이에 쓸 첫 줄 → 이렇게 풀어요 → 완성 답과 검산 → 주의할 점 → 조건을 바꾸어 생각해요** 순서다. 사용자 방식의 풀이를 start/solve/verify에 통합하고 이유·유도를 해당 단계에 연결한다. 별도 선행 핵심 풀이와 중복 상세 풀이를 만들지 않는다. 정리노트의 순수 개념 토픽은 기존 레이어 순서를 유지한다.

**한 행에 하나의 식:** 독립된 계산 대상은 각각 별도 display 블록/MD 줄/PDF 행에 쓴다. 서로 다른 $g_m$, $r_\pi$, $r_o$ 계산을 쉼표·\quad·\qquad로 한 줄에 묶지 않는다. 같은 양의 `식 = 대입 = 결과` 연속 등식과 실제 같은 값을 가진 소자의 등식 묶음은 유지할 수 있으며, 폭을 넘으면 단계별로 세로로 나눈다. 설명문의 짧은 기호·조건은 인라인으로 쓸 수 있다.

검토에서는 독립 계산이 실제로 별도 행/블록인지 HTML·동반 MD·답안 PDF 각각 확인한다. 같은 양의 연속 등식을 이유 없이 잘게 쪼개지 않는다. 현재 구형 route 추출과 새 통합 본문의 호환성을 확인하고, 미지원이면 발행을 보류한다. 문서 개정이나 정적 검사를 정상 발행/수학 검산/화면 검토로 간주하지 않는다.

   회로가 있는 토픽의 `CIRCUIT-02` 감사에는 그림의 측정 조건·입력/출력 접속·생략 근거·노드 관계·첫 식의 대응 위치를 적는다. $G_m$ 단락이 글에만 있고 그림이 일반 출력 노드이면 fail이다. $R_{out}$ 측정 회로에는 입력 영점 접속과 출력 시험원 방향이 있어야 한다. 유한 β 결과에 큰 β 관계를 쓰지 않았는지, 선택 모델에 필요한 상세 유도가 보존됐는지도 확인한다. $R_{out}$은 위 예외가 아니면 formal도 근사식부터 시작하고 정확 전체 모델은 내부 검산에만 둔다. 입력 왼쪽/노드 아래 축퇴 저항과 병렬 전류원 왼쪽/출력저항 오른쪽/출력 맨 오른쪽의 전체 배치를 확인하며 다른 토폴로지에 억지 적용하지 않는다. why-circuit 등 비적용 토픽에는 구체적 이유를 쓴다.

- 병렬 가지 순서 필수: 제어 전류원과 $r_o$가 병렬이면 반드시 **제어 전류원 왼쪽 → $r_o$ 또는 병렬 합성 저항 오른쪽 → 출력 접속 맨 오른쪽** 순서로 그린다. 입력은 그 왼쪽, 이미터/소스 축퇴 저항은 해당 노드 아래에 둔다. $r_o$를 생략한 축약 모델에는 없는 저항을 추가하지 않는다. 그 모델의 제어원 위치를 병렬쌍의 배치 규칙으로 일반화하지 않는다. 풀이 본문의 모든 SVG와 답안 PDF에서 소자·단자 전체 배치를 대조하고, 전기적 등가성만으로 위치 불일치를 승인하지 않는다.
- 노드 점과 시험 표기 필수: 접지 표기만 하는 비분기 단자와 접지 기호의 직접 접속점을 제외하고, 입력·출력·시험 노드와 이름을 붙인 전압 노드에는 연결 위치가 분명한 눈에 보이는 점을 찍는다. 출력 시험전압 노드의 점은 출력 도선의 실제 맨 끝이자 가장 오른쪽 단자에 둔다. 점 오른쪽으로 도선(ink)이 더 이어지거나 연장된 도선 중간에 점이 놓이면 안 된다. 시험 노드 전압 $V_t(+)$는 그 끝점 위에 둔다. 유입 시험전류는 오른쪽에서 왼쪽으로 흐르며, 왼쪽을 향하는 $i_t$ 화살표는 $V_t$ 점 왼쪽의 도선 구간에 둔다. $i_t$ 라벨도 점 왼쪽에서 그 화살표 아래나 곁에 둔다. 화살표 전체가 점 왼쪽에 머물고 점을 덮지 않도록 화살표 꼬리와 점 사이에 작은 간격을 남긴다. 화살표나 전류 라벨을 점 오른쪽에 놓지 않는다. 다른 시험 기호($v_x/i_x$ 등)를 쓰면 같은 배치와 정의를 적용한다. 선 교차만 있고 연결되지 않은 곳에는 점을 찍지 않는다. 라이트·다크 HTML과 실제 답안 PDF에서 점·라벨·화살표의 분리와 가시성을 각각 확인한다.

SVG에는 대응 노드 식별자와 색을 명시하고, HTML 테마와 PDF에서 실제 계산된 색이 파랑/빨강인지 확인한다. PDF의 문항 종류별 초록/주황 `--kind`를 노드 파랑의 대체값으로 사용하지 않는다. 풀이 본문의 모든 SVG와 MD에 참조된 같은 그림, 라이트·다크 HTML 및 실제 답안 PDF에서 접지 점 생략·가까운 라벨·점/전압 색 일치를 검토한다.
- 출력저항 표시/검산 경계: $R_{out}$은 처음부터 유효한 근사식으로 시작하고 조건과 $\approx$를 유지한다. 이 규칙은 생성하는 풀이 본문(start/solve/verify·formal/보충 포함) HTML·요약·동반 MD·답안 PDF 모두에 적용한다. 정확식 → 근사식 유도나 정확식과 수치 비교를 학습 본문에 추가하지 않는다. 정확한 $R_{out}$의 전체 모델·유도·수치/극한 대조는 내부 독립 검산 evidence에만 둔다. 원문이 정확식·유한 β 전체 결과 또는 수업 기본 큰 곱 근사와 반대인 조건·수치를 명시하면 예외 이유를 짧게 밝히고 필요한 모델과 결과를 제시한다. 유한 β 또는 $r_o$가 있다는 사실만으로 예외를 선언하지 않는다. 이 제한은 $R_{out}$에 한정하며 다른 개념의 필요한 상세 유도를 줄이지 않는다.
2. **누락**: 요약의 핵심 내용·강조 발언·미룬 유도 중 노트에 없는 것. $R_{out}$ 정확식 유도를 내부 evidence에만 둔 것은 위 예외가 아닌 한 누락으로 지적하지 않는다. 같은 뜻의 인용을 대표 하나로 합친 것도 누락이 아니다. 합쳐진 인용에 다른 정보(조건, 수치, 예외)가 있었다면 누락으로 지적한다.
3. **범위**: "예고만/안 다룸" 내용이 본문에 설명되어 있는가.
4. **ELI5 품질**: 쉽게 말하면(eli5) 레이어가 필요한 용어를 짧게 풀어 쓴 1~3문장인가. 첫 설명과 작은 예시만으로 다음 결과를 예측할 수 있는가. content-rules.md의 "이해되는 설명의 순서"대로 핵심 동작·작은 예시가 유도보다 먼저 나오며, 그림과 요약이 같은 규칙을 보여 주는지 확인한다. 작성자의 적용 질문을 직접 풀어 답·이유·조건을 대조한다. pole 예시라면 −40 다음 −60 dB/dec를 추론하고, 이득의 순간 하락과 기울기 변화를 구별할 수 있어야 한다. 정의·구조 토픽은 작은 사례에서 정의를 식별할 수 있는지 확인한다. 비유나 쉬운 단어가 있다는 이유만으로 통과시키지 않는다. 핵심 동작이 유도 뒤에 묻혀 있거나 예시로 규칙을 적용할 수 없으면 Important로 지적한다.
   **길잡이**(content-rules.md "정확히 말하면의 길잡이"): formal 소제목이 실제 내용 단위와 맞는지, 구간마다 굵은 문장이 그 구간의 결론이고 원문 문장인지, 굵은 글씨만 이어 읽어도 흐름이 서는지 확인한다. 토픽 끝 확인 질문을 본문만 읽고 직접 풀어 답·계산 한 줄과 대조하고, 본문 예시와 같은 절차인지(처음 보는 절차를 요구하지 않는지) 확인한다. 답이 틀리거나 본문으로 풀 수 없으면 Important, 소제목·굵은 결론이 내용과 어긋나면 Minor로 지적한다. 접기(`details`)로 본문을 숨기거나 토픽 머리에 질문을 둔 것은 Important다.
5. **문제 선별**: `problem-selection.md`의 exam-first-v2를 적용한다. 최대 20개·다른 회차 사용 문항 항상 제외·전제 순서를 확인한다. 미사용 기출 전체의 검토 기록과 원문/실제 그림/모든 소문항을 읽어 범위 적합성과 기출 우선 이유를 확인한다. 참고 풀이가 없으면 직접 풀며 해설 유무를 선발 가중치로 삼지 않는다. 교과서 문제는 부족한 목표 보완인지, 핵심/추가·추정 시간·소문항 묶음 수가 적절한지, coverage에 빠진 목표와 사유가 있는지 확인한다. 고정 종류 비율·절마다 최소 1개는 요구하지 않는다. 범위 밖 소문항은 전체 문항을 보류하고 미학습 개념을 기록한다. 이전 팩 보류 목록과 전체 시험 범위 빈틈/다른 ID 간 반복도 검토한다. 자동 schema 검사는 이러한 의미 검토와 독립 검산을 대신하지 않는다.
6. **표현**: 표 첫 열이 한 글자씩 줄바꿈되거나 빈 칸이 있는 표, 잘린 문장.
7. **첫 페이지(`why-circuit`)**: `content-rules.md` "왜 쓰는가 페이지"의 4단계(문제 / 단순 해법과 한계 / 핵심 아이디어 / 대가와 쓰이는 곳)를 모두 갖췄는가. 뒤 토픽의 유도를 되풀이하지 않는가. `<a href="#…">` 링크가 실제로 그 내용을 다루는 토픽을 가리키는가. 범위의 회로가 모두 나오는가.

개인화 감사는 다음 형태로 실제 검토 후 기록한다. `not_run`을 시작 상태로 쓰고, 적용 위치/내용 또는 `not_applicable` 이유와 reviewer를 채운 뒤에만 해당 토픽을 `pass`로 둔다. 기계 검사는 형식·집합·해시만 확인한다.
```json
{"learning_style": {"path": ".claude/skills/ec2-review-pack/references/solution-style.md", "sha256": "<현재 snapshot>", "rule_ids": ["<전체 규칙 ID>"]},
 "items": {"<topic ID>": {"status": "not_run", "reviewer": "", "rules": {
   "<규칙 ID>": {"disposition": "applied", "evidence": ""}}}}}
```
문제 없는 토픽도 감사하며 회로/계산 규칙이 비적용이면 구체적 이유를 쓴다. `learning-style-audit.json` 외 리뷰 보고 형식:
```
## Critical
- [s2-rout] 문제 → 고칠 내용
## Important
- [P9.12] …
## Minor
- …
```
각 항목은 토픽 id 또는 문제 id로 시작한다. 없으면 "없음".
